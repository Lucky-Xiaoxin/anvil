## 2. 行为口径

### 2.1 扫描与识别

- **源根自身是比赛**：源根直接内容里 ≥2 个题号形态题目（`A` / `B1` / `1001` / `CF1234A` / `ABC300F` 及 `-` / `_` 写法）→ 源根生成 `contest-group`。
- **源根是容器**：否则源根的直接子目录也可以各自成为比赛题组；比赛不再嵌套比赛（源根成为比赛后，孙级目录只按子题 / 共享文件处理）。
- **单文件题**：标题取不含扩展名的文件名；同目录同 stem 的 `.in` / `.out` / `.ans` 一并复制；其它文件不自动并入。
- **目录题**：顶层有主源码即成立；题号目录还可在一层范围内找到主源码（低置信）。目录题复制范围内全部非忽略普通文件，保留相对路径。
- **比赛共享文件**：比赛根下不归属任何子题的文件（README / PDF / 数据 / 公共脚本）进入 contest 自身，只计 `contest.fileCount`。
- **未判定**：没有主源码但有文件的目录停在 `undecided`，默认不选；用户勾选即确认成题目。
- **忽略**：沿用 5a 忽略表；源树内部符号链接 / junction 进入忽略统计（不复制、不拒绝整次扫描）；源路径本身的任一级组件是链接 → 拒绝扫描。
- **限制**：目录深度 16、文件 10,000、总字节 1 GiB、单文件 128 MiB、候选 2,000；任一超出返回 `import-limit`，不截断。
- **只读**：扫描只 `lstat` / `readdir` / 读文件 / 算 hash；plan 只在内存，不写受管根。

### 2.2 指纹与重复

- 文件 hash = 原始字节 SHA-256（不归一化换行、不去 BOM、不按文本解码，小写 hex）。
- 对象指纹按 POSIX 相对路径排序后拼 `<path> NUL <size> NUL <sha256> LF`，再 SHA-256；比赛包含共享文件与全部子题文件，子题前缀相对比赛根，因此同内容比赛换一个父目录名仍判同指纹。
- 重复矩阵：
  - 同源 + 同指纹 + 历史目标存在 + objectId 找得到 → 自动跳过并链接旧对象。
  - 同源 + 同指纹 + 目标消失 → 允许重新导入。
  - 同源 + 指纹变化 → 「来源有新版本」，默认不选，可导入新副本。
  - 不同源 + 同指纹 → 「潜在重复」，默认不选，必须明确「仍导入副本」。
  - 同批不同路径 + 同指纹 → 保留第一个为主候选，其余标潜在重复；不自动合并。
- 重复判定按**原子单元根**做；比赛子题跟随比赛单元，拆出的子题单独检查自己的来源快照。

### 2.3 plan / 提交 / 发布

- planId 32 位随机 hex；有效期 30 分钟；单进程保留最近 3 个；重启失效；不改受管根。
- plan 绑定扫描时的 `root realpath` + `.anvil/root.json.createdAt`；切换根 → 409 `import-root-changed`。
- commit 在 WorkService 写队列内先整体校验选择；不合法 400 `import-conflict` 且不创建 manifest。
- 原子单元：未分组题目 / 拆出的子题各自一个；contest + 最终仍挂载的选中子题一个；空题组（无子题且无共享文件）不合法。
- 每个单元：源快照复核（路径、文件集合、size / mtime / 重新 hash、对象指纹）→ staging 复制并复核 → `mkdir` 目标父目录 → 同卷 `rename` → 重建索引按全部 objectId 对账 → manifest `success`。
- 单元失败不回滚其它单元；一旦合法批次开始执行，接口仍返回 200，由 unit 状态表达部分成功。
- 同一 plan 重复 commit 返回同一结果；commit 进行中重复请求复用同一 Promise。

### 2.4 journal 与恢复

- manifest 同时是审计与崩溃 journal；`status: running → completed | partial | failed`，unit `planned → staged → published → success | failed`。
- 冷启动静默执行一次恢复；每次 commit 前也先对账。`planned/staged` + 最终路径不存在 → 只清理带合法 `staging.json` 的 staging 并标 failed；`staged` + 最终路径存在 → 按 unit 全部 objectId 对账；`published` 缺对象 → 保留现场报错；已 success 不重复复制。
- 源目录永不因恢复被删除或回滚。
- 坏 manifest 只产生警告，不影响工坊对象树。

### 2.5 打开方式

- `auto`（省略 app）：保持 5a 行为——文件夹 Explorer 优先、文件 VS Code 优先，失败互相回退。
- `vscode`：只走 VS Code，目录 `Code.exe --new-window <abs>`；失败 502 `editor-unavailable`，**不回退** Explorer。
- `explorer`：只走资源管理器，文件用 `/select,<abs>`。
- 本机 VS Code 安装把 Electron 资源放在版本目录（`<install>/<hash>/resources/app`），根 `Code.exe` 直接收 `--new-window` 会报 bad option；`codeLaunchFor()` 读取 `bin/code.cmd` 的版本目录，改为 `ELECTRON_RUN_AS_NODE=1 Code.exe <cli.js> --new-window <abs>`。官方布局仍直接 spawn `Code.exe`。
- 所有模式先走既有根内路径 / 符号链接校验；`spawn` 始终参数数组 + `shell:false`。

### 2.6 界面

- 中栏：`题组`（比赛组头带「比赛题组」标签）/ `未分组题目` / `模板` / `笔记`；problem 行常驻「题目」徽章；组头 `N 题` 仍是当前筛选结果内题目数。
- 导入预览：比赛组折叠、子题「题目」徽章、低置信 / 重复用文本 + 警告图标、逐项标题输入、题组归属下拉、undecided 勾选即确认、潜在重复的「仍导入副本」；全部原生 checkbox / input / select，可键盘操作。
- 显式状态：未选来源、扫描中、无候选、超限、plan 过期、源变化、全部重复、部分成功、manifest 警告、VS Code 不可用。
- 1280×900 实测无横向滚动；长路径中段省略并保留完整 `title`。

## 5. 已知问题 / 不处理项

1. **同批同内容**保留 plan 顺序里的第一个为主候选，其余标潜在重复；不做语义合并，也不把两边都默认关掉。这样同批只出现「潜在重复 1」，与手测口径一致。
2. **恢复触发**：冷启动静默对账一次、每次 commit 前再对账；没有单独的「恢复」UI。没有合法 `staging.json` 的残留目录一律保留现场，不删。
3. **mtime 严格**：源文件仅被 touch、内容未变也会判 `import-source-changed`（契约 §7.4 要求 size / mtime 快照未变）。重新扫描即可导入。
4. **大目录扫描**逐文件串行 hash；10,000 文件量级可能几十秒，扫描请求前端超时放到 5 分钟。
5. **重复判定在原子单元根**：比赛子题随整组；拆出的子题单独判定。不会把比赛里某道子题单独标成「潜在重复」。
6. **VS Code 启动布局**：支持官方布局与 `bin/code.cmd` 指向版本目录的布局；更特殊的安装若直接 spawn `Code.exe` 失败，显式 vscode 会 502，不回落 Explorer。
7. **plan 生命周期**：返回工坊只清前端状态，服务端 plan 仍在内存中保留到 30 分钟 / 最近 3 个 / 进程重启；没有取消 plan 的 API。
8. **全部为已导入项**时仍允许提交，会写一份零 unit 的 manifest（状态 completed），用于审计自动跳过；不会复制任何文件。
9. **模板 / 笔记不导入**；undecided 只停在预览，不写 `inbox/`；不做与旧目录的持续同步。
10. **结果 DTO 扩展**：`WorkImportResultUnitDto` 增加 `itemIds`（仅 API 展示失败单元用）；`.anvil.json` schema 与对象模型未变。
11. **目标文件 mtime** 是复制时间；源 mtime 只记入 manifest，不伪装成对象创建时间。
12. 前端没有 DOM 单测环境（技术锁不引 jsdom / testing-library）；组件行为由真机截图与纯状态派生测试覆盖。
