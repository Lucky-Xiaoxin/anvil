## 1. 背景

契约 23 §6.6 原写「v1 不做永久删除」，但 `e218eee`（结构修复批次）已经加入 `POST /api/work/trash/purge` 与前端两击清空，契约没有同步，形成「代码已有、契约仍说不做」的矛盾。

同时全站写接口没有跨站防护：服务只听 `127.0.0.1`，但不校验 Origin / Sec-Fetch-Site。清空接口不读请求体，任意网页一个跨站表单 POST 就能触发；其它写接口因为要 JSON + zod 校验，反而挡住了表单。清空是当时唯一「零门槛跨站」的破坏性入口。

## 2. 本次口径（2026-10-28 已拍板）

| 项 | 口径 |
|---|---|
| 永久删除范围 | 只保留整站「清空回收站」，不提供单项永久删除，不提供 `DELETE` 语义的对象硬删 |
| 删除判据 | 只删应用生成的条目：普通目录且目录内有普通文件 `trash.json`；文件、符号链接、缺 manifest 的目录、杂项一律不碰 |
| 确认方式 | 前端两击（第一次进入「确认清空」）+ 服务端必须收到 `{ confirm: true }`；失焦 / 切视图 / 列表变化后复位 |
| 请求防护 | 全局 `/api/*` 写方法（POST / PUT / PATCH / DELETE）要求 `application/json`；带 Origin 时只认本机 host；`Sec-Fetch-Site: cross-site` 拒绝 |
| 非浏览器请求 | 缺 Origin 放行（curl、单测）；防护只针对「网页替用户发请求」，不是身份认证 |

## 6. 已知问题 / 不处理项

- 不提供单项永久删除；不能从回收站删除手放的文件 / 目录（非应用条目）。
- 跨站防护只覆盖写方法，不覆盖 `GET` 读取；同源页面内的恶意脚本不在防护范围（本地单用户工具的明确边界）。
- 本机其它 `localhost` / `127.0.0.1` 端口的页面仍在 Origin 白名单内（为兼容 Vite 5173）；它们触发清空仍需过 JSON content-type / CORS 预检，本次 7800 攻击页即在这两道被挡。若以后要求连本机其它页面也按 Origin 拒绝，需把白名单收窄到固定端口。
- 清空失败时按「已删除 N 项」报错，不做事后回滚（删除本身不可逆）。
