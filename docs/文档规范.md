# ANVIL 文档规范

> **状态：现行。** 本文定义 `docs/`、根 `README.md`、`AGENTS.md` 与 `design/` 的文档类型、命名、状态、必备内容、索引规则和收工检查。
> **日期**：2026-10-23。
> **目的**：让「当前该看哪份、哪份是历史、实现报告该写到什么程度」不再依赖临时开 agent 检查。

---

## 1. 总原则

1. **一类文档只干一件事。** 契约定义「应该是什么」；报告记录「实际做了什么」；参考记录「外部事实」；提示词和 brief 是开工输入；archive 只留历史。
2. **同一事实只有一个权威位置。** 当前行为以现行契约为准；实现证据以交付报告为准；外部数据以 reference 为准。不要在 README、AGENTS、报告里复制整段规格。
3. **历史不可覆盖。** 交付过的报告、历史契约、旧 brief 不按今天的新口径重写；需要改变口径时新建契约或新增「补记」，并更新索引与旧文档头部的状态说明。
4. **文档必须可核对。** 测试数字、截图、提交号、外部数据都要有来源；没有证据的结论不写进报告。
5. **仓库里不放临时产物。** 浏览器 profile、截图草稿、驱动脚本、agent 原始日志一律放系统 temp；仓库只留可交付文档、正式截图和基线。
6. **索引先行。** 新文档创建时同步更新 `docs/README.md`；不能让文档只能靠搜索或记忆找到。

## 2. 文档类型与落点

| 类型 | 目录 | 回答的问题 | 是否定义当前行为 |
|---|---|---|---|
| 文档索引 | `docs/README.md` | 现在该读什么、历史文档在哪 | 否，只导航 |
| 项目规则 | `AGENTS.md` | 技术锁、分支、卫生、当前阶段 | 部分是（流程与约束） |
| 产品概览 | 根 `README.md` | 项目是什么、怎么启动、模块有哪些 | 否，概览 |
| 契约 / 规格 | `docs/contracts/` | 下一片 / 当前片的行为、边界、验收 | **是** |
| 交付报告 | `docs/reports/` | 本批次实际完成了什么、测试多少、遗留什么 | 否，记录事实 |
| 审计 | `docs/reports/` | 某提交的只读审查结论与后续处理 | 否，历史证据 |
| 数据源参考 | `docs/reference/` | 外部接口 / 第三方数据实测 | 否，事实参考 |
| 开工提示词 | `docs/prompts/` | 某批次交给 agent 的任务清单 | 否，历史输入 |
| 设计 brief | `docs/briefs/` | 某视觉稿的目标、状态、交付要求 | 否，历史输入 |
| 归档 | `docs/archive/` | 问卷、旧草案、讨论记录 | 否，背景 |
| 视觉基线 / 截图 | `design/` | 冻结的视觉稿与验收截图 | 视觉基线只读 |

**禁止的落点：**

- 不在仓库根新增说明文档；根目录只保留 `README.md` 与 `AGENTS.md`。
- 不在 `docs/` 下创建 `tmp/`、`draft/`、`notes/` 之类的临时目录。
- 不把 agent 原始长文、会话记录、临时审查稿放进 `docs/reports/`；报告必须是蒸馏后的结论。
- 不把实现报告当契约；报告不能覆盖现行契约。

## 3. 命名与编号

### 3.1 契约

- 新文件：`docs/contracts/NN-主题契约.md`。
- `NN` 为递增两位编号；已有编号不复用、不重排。
- 主题用简短中文；文件名不加日期。
- 一个主题只有一个现行契约；被替代时新建文件，不原地改掉旧口径。

现有编号到 `25-工坊-批量题组导入契约.md`；下一篇契约从 `26` 起。

### 3.2 报告与审计

- 实现报告：`docs/reports/实现说明-<批次>.md`。
- 审查：`docs/reports/审查结果-YYYY-MM-DD.md`。
- 修复批次：`docs/reports/实现说明-<批次>-修复.md`；如果修复属于同一交付，也可以在报告内加「修复批次」章节，由报告头部说明。
- 报告不编号（早期带编号的报告保留原名，不追溯改名）。

### 3.3 提示词、brief、reference、archive

- 提示词：`docs/prompts/NN-实现agent-开工提示词-<批次>.md`。
- 设计 brief：`docs/briefs/NN-设计brief-<主题>.md`。
- 数据源参考：`docs/reference/NN-<主题>.md`。
- 归档：`docs/archive/NN-<主题>.md`。

统一使用中文主题、ASCII 连字符、ISO 日期 `YYYY-MM-DD`；不要用空格和版本号堆叠。

## 4. 状态与生命周期

### 4.1 状态词

| 状态 | 含义 | 能否作为实现依据 |
|---|---|---|
| `草案` | 已写出，尚未批准 / 尚未实现，可能改动 | 只能作为讨论依据 |
| `现行` | 当前实现依据 | **是** |
| `参考` | 外部实测资料，仍在被引用 | 是（仅限事实参考） |
| `历史` | 已交付快照，不再施工 | 否 |
| `作废` | 已被新文档明确取代，仅留痕 | 否 |

### 4.2 状态转换

```text
草案 → 现行 → 历史
          ↘ 作废（被新契约替代）
```

- 契约在实现合并后，把状态从 `草案（待实现）` 改为 `现行`；如果被下一片替代，改为 `历史` 或 `作废`，并在头部写明替代文档。
- 报告、提示词、brief 交付后统一标 `历史`；报告例外地需要更正事实时，不重写结论，追加 `> **补记 YYYY-MM-DD**：...`。
- reference 被新实测取代时标 `历史`；仍在使用但只是参考时标 `参考`。
- archive 默认 `历史`。

### 4.3 头部格式

新文档统一使用：

```markdown
> **状态**：草案 | 现行 | 参考 | 历史 | 作废
> **日期**：YYYY-MM-DD
> **依据**：上游契约 / 用户决定 / 实测来源
> **关联**：相关文档的相对路径
> **实现**：分支 / 提交号 / 报告（仅契约与报告需要）
```

旧文档只在被修改时补齐头部，不做全仓一次性改写。

## 5. 各类型的必备内容

### 5.1 契约

至少包含：

1. **已拍板**：用户已确认、不再反复讨论的决策；
2. **一句话目标**；
3. **交付物（DoD）**：可验收的结果，不写“尽量”“完善”；
4. **范围 / 不做**：明确防跑偏；
5. **语义与数据**：对象、字段、生命周期、兼容性；
6. **API / DTO**：请求、响应、错误形状；
7. **安全边界**：路径、权限、源目录、原子性；
8. **界面 / 状态 / 交互**：空态、错误态、键盘、1280 宽度；
9. **测试与验收**：单测、API、纯函数、手测、verify 基线；
10. **实现约束与建议落点**；
11. **与其他契约的关系**：保留 / 改写 / 取代了什么。

契约不写实现流水账，不列 agent 工作日志。

### 5.2 实现报告

至少包含：

1. 分支、契约、开工基线、结束测试数字；
2. **完成度对照表**：契约条目 → 状态 → 落点 / 证据；
3. `npm run verify` 的实际结果；
4. 真机 / 截图证据（哪些图证明了哪个状态）；
5. 已知问题、不处理项、后续切片；
6. 主要改动文件与复现方式。

报告可以写“未做”，但必须与契约的「不做」区分：未做是缺口，不做是范围。

### 5.3 数据源参考

至少包含：

- 实测日期、请求方式、凭据 / 限速条件；
- 结论矩阵：能拉什么、怎么拉、实测结果、风险；
- 与旧结论的差异和更正日期；
- 不可复现 / 不稳定的地方要显式标注。

### 5.4 开工提示词

至少包含：

- 交付对象、分支、开工基线、必读契约；
- 任务清单（可勾选）；
- 技术锁与禁止项；
- 自测与交付物；
- 历史口径变更提醒（哪些旧段落作废）。

提示词是历史输入，交付后不按它继续施工。

### 5.5 设计 brief

至少包含：

- 设计对象与目标产物文件名；
- 视觉基线（tokens / 组件 / 动效）；
- 必须覆盖的状态和响应式 / 可访问性要求；
- 明确不做的视觉范围；
- 截图与交付清单。

### 5.6 审计

至少包含：

- 审查的提交 / 分支、范围、只读声明；
- 基线命令与数字；
- 发现按严重度列出，每条有文件 / 行号或可复现证据；
- 已解决 / 未解决 / 不处理的归属；
- 不把审计当成新的行为契约。

## 6. 索引与链接规则

1. **`docs/README.md` 是唯一文档入口。** 新文档创建当次就加入对应表格；不能“以后再补”。
2. **`AGENTS.md` 只放当前阶段、技术锁、流程和当前契约入口。** 不在 AGENTS 复制历史报告内容。
3. **根 `README.md` 只放产品概览和当前常用文档入口。** 不堆历史列表。
4. **当前契约表**只列现行 / 草案中的下一片契约；历史契约放历史表。
5. 新契约替代旧契约时，必须同时：
   - 更新 `docs/README.md` 的状态和说明；
   - 在旧契约头部加「由 XX 替代 / 部分接管」；
   - 更新 `AGENTS.md` 的当前契约指针（如果切片阶段变化）。
6. 文档内链使用仓库相对路径；不要把绝对本机路径写进正文。
7. 链接检查是收工必做项；不能留下指向不存在文件的死链。

## 7. 收工检查清单

每次实现 / 文档批次结束前逐项确认：

### 开工

- [ ] `git status` 已知，工作树没有意外未跟踪文件。
- [ ] 当前分支明确；需要新分支时已经过用户同意。
- [ ] 读了 `AGENTS.md`、`docs/README.md` 和当前契约。
- [ ] 记录了 `npm test` / `npm run verify` 的基线数字。

### 文档

- [ ] 新契约 / 报告有统一状态头、日期、依据、关联。
- [ ] 契约的「不做」和报告的「未做」没有混写。
- [ ] 报告里的测试数字来自实际运行，不是推测。
- [ ] 新文档已进入 `docs/README.md`。
- [ ] 当前契约指针和 AGENTS 的当前阶段一致。
- [ ] 旧文档只加状态 / 替代说明，没有按新口径重写历史结论。
- [ ] 没有死链、临时文件、草稿截图或 agent 原始长文入库。

### 实现 / 交付

- [ ] `npm run verify` 通过。
- [ ] 真机 UI 验证；截图放在 `design/_shots/`，文件名能对应验收项。
- [ ] 只关闭自己启动的服务 / 进程。
- [ ] 改动只在本批次分支提交；未跟踪文件已清理或明确说明。
- [ ] 交付报告包含完成度、测试、截图、已知问题。
- [ ] 需要合并 `main` 时使用 `--no-ff`，且已经过用户同意。

## 8. 建议的自动化检查

当前先按 §7 手动检查。后续可以落一个无依赖的 `npm run docs:check`，检查：

- `docs/**/*.md` 是否都在 `docs/README.md` 出现；
- 契约是否具备状态头、日期、测试与验收章节；
- `docs/README.md` 中的相对链接是否存在；
- `AGENTS.md` 指向的当前契约是否存在；
- `design/_shots/` 是否出现明显临时文件；
- 仓库根是否出现规格外的 `.md`。

新增该脚本属于独立小批次，不在本规范落位时顺手改代码。
